# 4. Reference import

## 4.1 Scope and sources

- Input packs: every `*.pack` under the game `data/` directory that carries `db/` or `.loc` entries, in engine load order (R5 D: type Boot 0 → Release 1 → Patch 2 → Mod 3 → Movie 4, alphabetical within type, last copy of a path wins; the list of enabled Mod packs is read from `<game>/used_mods.txt`, today empty). Today exactly one pack (`db.pack`, 1,521 tables) carries `db/` and `local_en.pack` carries 235 of the 373 `.loc` files (R5 D, F); the builder still walks all 261 packs (`pack_scan.json`: index-only scan of 261 packs, 0 errors) so a future patch/mod pack is picked up with no code change. Language: `local_en` only (the only language the consumers read, R5 F).
- Schema: `D:\twdata\reference\ui3_extraction\schema_wh3.ron` (format version 5; 1,663 definitions, 2,231 versions; 100% of the 1,520 decodable tables have a definition at the pack's header version, R5 A). The pack's header version selects the definition; `autoresolver_unit_group_categories_enums_tables` (no definition, 0 rows, 91 bytes) is recorded in `ref.table_meta` with `n_cols = 0` and no table.
- Decoder: `advisor/reference/build_reference.py` `_read_field` (12 types, covers all 11 RON types; R5 A) with two changes: no `round(…, 4)` on F32/F64 (5.3% of F32 values were altered, type_census) and `OptionalStringU8` absent → `None` instead of `''` (70.1% of optional values are absent, 0 present-but-empty, so NULL vs '' is lossless in both directions).

## 4.2 Schema layout

One table per pack table in schema `ref`, named by the folder stem without `_tables` (`db/character_skills_tables/` → `ref.character_skills`); columns in `ca_order` with RON names (quoted identifiers; 4 RON names collide with SQL keywords, e.g. `key`, `order`, `group`, `end` — quoting handles them). Metadata in `ref.table_meta`/`ref.column_meta` (03c). A build writes into schema `ref_build`, validates, then renames `ref` → `ref_prev` and `ref_build` → `ref` in one transaction (4.6). `ref_prev` is dropped after the dictionaries have been re-resolved (4.5). Consumers use unqualified names with `search_path = ref` or qualified `ref.<tbl>`; nothing references `ref_build`.

## 4.4 Keys and foreign keys (R5 B-C; policy C10)

- **Primary key** = the RON `is_key` columns, declared on all 1,520 tables: 0 tables have duplicate keys in data (decode_probe KEYS line; recount R5 B), 952 single-column, 568 composite (2-12 columns). Key column types include 96 OptionalStringU8 (absent → NULL): a NULL in a PK column is illegal, so those columns are declared `TEXT NOT NULL DEFAULT ''` **in key position only**, and `ref.column_meta.default_value` records the substitution; the 14 Boolean and 3 F32 key columns are declared as-is (equality on `REAL` is exact for stored values).
- **Foreign keys**: declared for a relation `(src.col → tgt.col)` iff (a) `tgt` exists in the pack (653 of 861 target tables; 323 relations to absent tables are recorded in `column_meta.fk_declared = false`), (b) `tgt.col` is the target's PK or has a UNIQUE index (654 of 656 target pairs; `unit_variants.name` and `campaign_map_playable_areas.campaign_key` are non-unique → no FK, 2 relations), (c) non-empty values resolve ≥ 99.9% (2,450 relations at 100% declared; the 3 `cdir_events_mission_*_junctions.mission_key → missions.key` relations at 99.89-99.92% are **not** declared and their 2-8 orphan keys are listed in `column_meta.ref_resolved`), (d) types agree after the cast rule: the 11 relations where a StringU8 column references an I64/I32 key (or vice versa) resolve 100% after `str()` (R5 C) — for these the referencing column is loaded as the target's type (`BIGINT`/`INTEGER`) when every value parses, and the FK is declared; `cai_decision_items.culture_occupation_decision` (77/1,574, `0` sentinel) is not declared. Total declared FKs ≈ 2,461; each FK gets a supporting index on the referencing column only when the referencing table has > 1,000 rows (FK checks on load are one-off; the corpus never writes `ref`).
- Self-references (17) are declared. FK validation happens at build time in the `ref_build` schema (a failing FK fails the build — the manifest row is marked `failed` with the constraint name; nothing is swapped).

## 4.5 Dictionaries after a build

After the swap, `dict.resolve()` runs for every family in `dict.family`: `UPDATE dict.<f> d SET is_reference = EXISTS (SELECT 1 FROM ref.<ref_tbl> r WHERE r.<ref_col> = d.key), ref_build_id = CASE WHEN EXISTS(...) THEN <build_id> ELSE NULL END WHERE is_reference IS DISTINCT FROM EXISTS(...)`; the count of flips per family is written to the manifest's log; a key that disappears from the game data becomes an explicit non-reference row (its corpus rows keep referencing it). New keys observed by the collector are inserted by the writer with `is_reference` computed against the live `ref` at insert time (07 §7.3). `agent_subtype` resolves against `ref.agent_subtypes` (586/586, M3 B) — the permitted-subtypes junction is no longer the resolution target.

## 4.6 Manifest, change detection, build procedure, timing

**Fingerprint** = SHA-256 over the ordered concatenation of, for every pack in load order: `name, sha256(file bytes), size, mtime`; plus `sha256(schema_wh3.ron)`; plus the exe `FileVersion` (`collect._game_version`, `8.1.1.0`; R5 E) and the Steam `buildid` from `appmanifest_1142710.acf` (24237342). Hashing 261 packs (~8 GB, of which `data.pack` 403 MB and `data_maps.pack` 419 MB dominate; R5 D) costs one sequential read; the fingerprint is computed from `(name, size, mtime)` first and the full sha256 only when that triple changed for any pack — both are stored, so a mtime-only touch (Steam verify) still yields "unchanged" when the sha256 matches.

**Trigger**: `python -m advisor.reference.build_reference` is invoked (a) by `runctl.up` before starting the recorder and (b) by the recorder at start; both compute the fingerprint and compare with `ref.manifest WHERE status = 'live'`: equal → exit 0 in < 1 s (no DDL, no writes); different → build. The recorder refuses to record while a build is `building` (it waits, logging every 10 s) so no snapshot references a dictionary resolved against a half-built reference.

**Procedure** (one psycopg connection, one transaction for the swap; the load itself runs in `ref_build` outside the swap transaction so a crash leaves only a droppable schema):
1. `INSERT INTO ref.manifest (status='building', …) RETURNING build_id`; `DROP SCHEMA IF EXISTS ref_build CASCADE; CREATE SCHEMA ref_build`.
2. Parse RON once (10.8 MB; today's `ron_schema.py` parser), decode all packs in load order (decode 1.6 s for 865,404 rows, decode_probe), merge by table (later pack wins per row key).
3. For each table: `CREATE TABLE ref_build.<tbl> (...)` without constraints; `COPY ... FROM STDIN (FORMAT binary)` via psycopg `copy()`; then `ALTER TABLE ADD PRIMARY KEY`. 865k rows over 1,520 tables: COPY throughput ≥ 200k rows/s for narrow rows (ASSUMPTION; verified by the first build's `build_seconds`), so ≈ 5 s of COPY + 1,520 × ~15 ms DDL ≈ 25 s.
4. `.loc`: decode 241,972 entries (0.40 s, R5 F); split each key into `(tbl, col, key)` by matching the longest `<tbl>_<col>_` prefix among the RON `localised_fields` of the `.loc` file's own table stem (`text/db/<tbl>__.loc`; 220,840 keys match, 91.3%); the remaining keys (`uied_*`, `building_*_texts_*`, `encyclopedia_*`, …; 8.7%) get `tbl` = file stem and `col = ''`, `key` = the remainder — a defined rule, not a fallback; `loc_key` keeps the raw key for consumers that look up by full key. COPY 242k rows ≈ 2 s.
5. FKs: `ALTER TABLE ... ADD FOREIGN KEY` for the ≈ 2,461 declared relations (4.4) — each validates by an index/hash join over ≤ 65k rows; ≈ 2,461 × 20 ms ≈ 50 s (ASSUMPTION; measured on first build).
6. `ANALYZE` every table (≈ 1,520 × 5 ms).
7. Swap transaction: `ALTER SCHEMA ref RENAME TO ref_prev; ALTER SCHEMA ref_build RENAME TO ref; UPDATE ref.manifest SET status='superseded' WHERE status='live'; UPDATE ref.manifest SET status='live', finished_ts, n_tables, n_rows, n_loc, build_seconds WHERE build_id = ...; COMMIT`. `ref.manifest`/`table_meta`/`column_meta`/`loc` live in `ref` and are moved with it; `manifest` rows are copied into the new schema's table before the swap (the manifest table is rebuilt from `ref_prev.manifest` + the new row). `dict.resolve()`; `DROP SCHEMA ref_prev CASCADE`.

**Expected build time**: decode 2.7 s + COPY ≈ 7 s + DDL/PK ≈ 25 s + FK ≈ 50 s + ANALYZE ≈ 8 s + fingerprint (sha256 of 8 GB at ≥ 1 GB/s NVMe ≈ 8 s, only when a size/mtime changed) ≈ **100 s**, well under the 3-minute budget (01 W12). Today's builder (per-row DELETE+INSERT, 34 DROP+CREATE sites, manual, no versioning; R5 G) is deleted.

**Prepared-statement/plan caches**: renaming schemas invalidates plans referencing `ref.*` in live sessions automatically (relcache invalidation); `features_db`'s process caches (`_lookup_cache`, `_res_cache`; R2 C) are keyed by key text and would serve stale rows after a rebuild — they are invalidated by comparing `ref.manifest.build_id` on each lookup miss... no: on every call they would add a query. Rule: the advisor session reads `build_id` at start and at each campaign boundary (`session.py` boundary pass); a change clears the caches. The GNN corpus fingerprint (`corpus.py:44-65`) becomes `build_id` + schema hash (T10).
